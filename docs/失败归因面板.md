# 新增需求：失败录屏分析与失败归因面板

来源：2026-10-21 用户要求在后续测试时输入失败录屏，由助手总结本次失败原因，并制作“失败归因面板”，把翻车原因拆解到具体层级。状态：已纳入第一版规格，分析流程与面板尚未实现；当前未收到失败录屏。

## 输入与分析流程

2026-10-23 用户明确：最终由软件接入 LLM，对导入的失败录像进行分析并生成面板，不能仅交付聊天中的人工分析。首版须有基础可用版本，稳定通关优先，后续完善分析深度和交互。首选模型及验收见 `../config/product-requirements.json`；具体 API、可用模型 ID 及视频输入方式在接入时验证，当前未连接。模型输出同样遵守下列证据与不确定性要求。

用户提供失败录屏后，保留原文件及 SHA256，建立独立 `review_id`，记录来源、时长、画面尺寸、是否完整，以及人工／Agent／混合操作来源。关联已知 `run_id`；无法确认时留空，不凭文件名猜测。允许仅凭录屏开始复盘，不把运行日志作为提交前提。

先核实可见结局。未录到失败画面时标记“用户报告失败，录像结局未核实”；录像截断、遮挡、菜单暂停、接管等区间明确标注。以视频时间戳定位关键画面，不用视频导出尺寸生成点击坐标。

从失守位置向前回溯，找出最早有证据支持且可能影响结局的偏差、局势恶化过程、临界时刻及最终表现。必要时检查连续帧，不能仅凭一张终局图断言整局原因。总结主因、促成因素和待确认项，形成可追溯的因果链；同一局可以有多个因素，不能强行找唯一根因。

## 归因层级

“层级”用于由现象追到决策及技术环节，不代表每次失败都经历全部层级。环境问题可跨层影响；按证据建立具体关联。

| 层级 | 要回答的问题 | 典型归因与所需依据 |
| --- | --- | --- |
| L0 失败表现 | 哪里、何时失守，实际看到了什么？ | 突破行、失去的关键植物、可见失败画面及对应时间；现象本身不能直接当根因 |
| L1 阵型与资源 | 哪个防线缺口或资源状态直接促成失守？ | 某行输出／阻挡不足、水路缺口、补损不及时、可见阳光不足；不得编造精确伤害、血量或冷却 |
| L2 战术与目标选择 | 当时应对的目标、投入顺序或位置是否合适？ | 忽略受压行、阶段目标不适配、过度发育、为对称延误防守；结合当时可见资源、可用卡片和威胁判断 |
| L3 感知与状态理解 | 系统是否及时、准确地识别了局势？ | 漏检僵尸、错行、占格／卡片／阳光识别错误；需对照录像和当时的观测输出，只有录像时不能确认系统内部漏检 |
| L4 决策时序与调度 | 正确的信息或建议是否过晚、过期或被错误排队？ | 请求延迟、快照陈旧、应急未抢占、旧动作未失效；需时间戳、请求和调度日志，录像通常只能支持“可见反应较晚” |
| L5 输入执行与结果验证 | 选卡、放置、收集、取消和结果确认是否实际完成？ | 点错槽／格、选择被打断、输入未生效、失败后未确认；对照执行记录、前后画面和窗口映射，区分计划、输入和成功落地 |
| L6 环境与交互 | 窗口、缩放、遮挡、焦点或人工接管是否影响前述环节？ | Magpie 映射变化、菜单／遮挡、窗口变化、人工干预；需画面或环境记录，不自动把问题归给模型 |

只有证据支持时才下钻到内部环节。视频可见的“没有补种”不能直接证明“LLM 判断错误”，还可能涉及卡片不可用、输入失败或状态未知。面板显示已证实、推测、待确认三种结论状态，附依据与缺失材料，不给无校准的概率或责任占比。

## 面板内容与交互

作为右侧栏的赛后复盘视图／标签页接入；支持折叠、滚动和展开层级，不遮挡游戏，不擅自改变窗口尺寸。当前约 228 DIP 的窄侧栏优先展示摘要和层级卡片，证据按需展开。

| 区域 | 内容 |
| --- | --- |
| 本局概要 | 录像来源、操作来源、结局确认状态、一句话失败总结、分析覆盖范围 |
| 关键因果链 | 从早期偏差到局势恶化再到失守；标明主因、促成因素、关联层级及不确定环节 |
| 分层归因 | 各层具体问题、首次可见偏差时间、影响、证据、结论状态；无证据层显示未确认／不适用 |
| 关键时间点 | 偏差出现、错失应对窗口、明显恶化和失守的时间与截图，可关联战术片段 |
| 改进与复测 | 针对具体问题的优先级、修改建议、可检验的预期及复测条件 |
| 未决问题 | 仍不能判定的原因，以及能够消除歧义的最少补充资料 |

点击原因可跳到对应录像时间、关键截图和已有时间轴事件。没有运行日志时仍可展示视频证据；缺失的请求／动作记录明确显示不可用，不生成伪造记录。导入录像与在线日志通过经验证的时间锚点对齐，保留偏移及误差；未对齐时保持两个时钟，禁止强行匹配。

分析以当时可获得的信息评估选择，事后新增推断标记为“赛后分析”，不改写在线阶段、目标或公开理由。可提出“若更早补某行，可能降低风险”的待复测假设；未验证不能写成“这样必胜”。

## 数据关联与交付

每次分析至少生成可读复盘摘要和结构化归因记录，供失败面板使用。后续实现时按 `evidence/reviews/<review_id>/` 组织来源清单、视频元数据／哈希、关键帧、报告与结构化记录，保留原始证据，不覆盖历史分析版本。

| 对象 | 最小字段 |
| --- | --- |
| 复盘 | `review_id`、`run_id`（可空）、`video_ref`、`sha256`、`actor_source`、`outcome_status`、`coverage`、`analysis_version` |
| 归因项 | `finding_id`、`layer`、`role`（主因／促成／未决）、`claim`、`conclusion_status`、`time_range`、`evidence_refs`、`missing_evidence`、`linked_finding_ids` |
| 关联 | 已有的 `segment_id`、`state_id`、`request_id`、`decision_id`、`action_id` 及结果引用；缺失时可空，不臆造 |
| 改进项 | `finding_id`、`priority`、`proposed_change`、`expected_effect`、`retest_condition`、`validation_status` |

此需求不代表已实现自动视频解析、失败归因或 UI，也不改变第 1—3 天完成状态和第 4 天下一步安排。

## 接入安排

- 第 6—8 天：观测和动作证据保留时间、来源及 ID，支持复盘追踪。
- 第 9—12 天：保留真实请求、公开决策摘要、动作校验和结果，支持内部环节归因。
- 第 17—20 天：在侧栏／复盘功能中接入分层归因卡片、关键帧及时间轴跳转。
- 第 21 天：回归检查视频与日志缺失、不一致、结局未录全的展示。
- 第 22—26 天：使用用户提供的失败录屏分析主因、安排修复及复测，保留失败样本与分析版本。

## 验收条件

- [ ] 提供失败录屏后能得到本局失败总结、主因／促成因素／未决项，以及具体层级拆解。
- [ ] 关键结论能定位视频时间戳与画面；涉及系统内部环节时有日志支持，或明确标为推测／待确认。
- [ ] 区分失败表现、直接原因和上游因素，保留多因果关联，不把最终失守等同于最早偏差。
- [ ] 仅有录屏也能完成有边界的复盘；不伪造模型思路、输入日志、精确数值或必胜反事实。
- [ ] 人工／Agent／混合操作、用户报告与画面核实、原始在线记录与赛后分析均能区分。
- [ ] 面板可展开具体原因并查看证据，与已有时间轴正确关联；浏览不暂停游戏或切换控制模式。
- [ ] 每项优先修复建议有对应归因项和复测条件，修复后的效果需复测确认。
